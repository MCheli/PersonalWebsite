## 2. Code review

The code was written by Claude Opus 4.6/4.7 in a handful of sessions and it shows in the good ways (pinned actions, slim images, key redaction, SSR crawler block) and the ways that older sessions tended to produce.

**Structure**
- `useTerminal.ts` had a `commands` object, a separate `shortcuts` map that duplicated catalog URLs by hand, and three commands (`services`, `weather`, `exit`) special-cased outside the registry — so `help exit` said "Unknown command", tab completion carried its own hand-maintained list, and adding a command meant touching four places.
- `app.vue` was `<script setup>` without TypeScript, with the run-a-command logic duplicated between `simulateTyping` and `handleKeydown`, a `document.addEventListener('mouseup', …)` never removed, and `v-html` of a regex-linkified string for output (escaped correctly, but it's the wrong tool: output should be structured and links should be elements).
- `commands[cmd]` indexing a `const` object with an arbitrary string — fine untyped, a type error under strict TS. There was no typecheck step, no ESLint, no `tsconfig` of its own, so none of this was caught.
- Column-padded `pre` text (`padEnd(22)`, 70-character rules) is why the catalog is unreadable on a phone; the layout was in the strings, not the CSS. `.suggestion-line { margin-left: 250px }` was a hard-coded alignment that broke at every width but one.
- Weather fetched `https://flask.markcheli.com/weather` as a string literal while `runtimeConfig.public.apiBase` and a Nitro `devProxy` sat unused.
- Empty Enter opened LinkedIn in a new tab (the "default command"), which surprises and gets popup-blocked. `exit` printed text and did nothing.

**Tests**
- 39 tests, all against the composable, with `ref` mocked as `{ value }` — so nothing exercised a component, SSR output, the DOM, or mobile. The API had 11 good tests including the key-redaction ones from PR #43.

**API**
- `datetime.utcnow()` (deprecated; warned on every run). `/weather` made one OpenWeatherMap call per visitor with CORS open to `*` — a public, unauthenticated proxy for a metered key. Now cached for 10 minutes per worker. Emoji `print`s in `__main__`.
- The Flask container is tiny; it could be Nitro server routes. Kept, because it is part of the "two containers" story in the catalog, it already has CORS and a public host, and it is the natural JSON endpoint for assistants. Revisit if it ever needs a database.

**Build, Docker, CI**
- CI was in good shape (SHA-pinned actions, PR builds without push, weekly fresh-base rebuild, slim-image smoke test). Missing: lint, typecheck, any content validation, concurrency cancel, screenshots.
- `frontend/Dockerfile` carries a symlink hack for `.output/server/chunks/public` that predates Nuxt 3.21; see the tooling report for whether it is still needed.
- `package.json` had `"dependencies": {}` and Google Fonts loaded from fonts.googleapis.com at runtime (a third-party request on every page view, and a CSP hole).
- `README.md` said Flask 3.0, `apiBase` default `/api`, and didn't list `/services`.

**Security** — fine. Headers present, no secrets in the repo, non-root containers, key redaction tested. Two notes: the weather proxy (above) and that the CSP is `frame-ancestors` only; a full CSP is possible now that the font is self-hosted, but Nuxt's inline hydration script needs a nonce or `'unsafe-inline'`, so it was left for a later pass.

## 3. Does it represent Mark and his portfolio?

**Not for the audience that matters now.** The site is a homelab catalog with a terminal skin. It is a good homelab catalog. But:

- The first screen says "Developer Terminal", a fake login line, a figlet, server specs. A hiring manager learns Mark's actual title only by typing `about`. On a phone, nobody types.
- There was no resume, no work history, no way to download anything, and no projects page — `services` listed containers, which is not the same thing. RigReady (the most substantial recent build), the LiDAR tool, the energy monitor and the receipt-printer brief weren't on the site at all because they aren't containers on the R630.
- Positioning was inconsistent across surfaces: "Developer" (profile), "Developer, Product Strategist, Homelab Operator" (title tag), "Software Engineer \| Infrastructure Enthusiast" (`whoami`), "director of Onshape's Product Operations & Strategy team" (`about`). The last one is the true one and the one a recruiter is cross-checking against LinkedIn.
- The OG image was the favicon, so a link shared in Slack or LinkedIn previewed as a tiny icon and the title.
- No photo (hiring managers expect one on a resume page).

What was right and is kept: the terminal personality, the SSR block for crawlers, the JSON-LD, the robots/sitemap, the "type a service name to open it" affordance.

**Positioning adopted** (see `PRODUCT.md`): *a product and operations leader who still ships code* — Director of Product Operations & Strategy for Onshape at PTC; thirteen years from intern to director; led engineering teams of 35+ and a 40-person org; owns analytics, PLG, AI adoption and localization ops; builds and runs a 40-container homelab. The first screen says this in plain text before anything else.

## 4. Features, mobile, the job search

What a visitor can do now that they couldn't:

- **Read it on a phone.** Output is structured blocks that wrap, not padded `pre`; the figlet gives way to the name under 640px; the input doesn't trigger iOS zoom; a sticky row of tappable commands (`about` `projects` `resume` `homelab` `contact` `help`) replaces typing.
- **Get the resume.** `resume` in the terminal; `/resume` as a readable, printable page; `/Mark-Cheli-Resume.pdf` generated from the same JSON. Education, certificates, skills by group, interests.
- **See the projects.** `projects` / `projects <slug>` and `/projects#slug` cards with tagline, description, stack chips, repo / live / demo links — eleven projects, four featured, all with public code behind them.
- **Reach him.** `contact` with a `mailto:` link, LinkedIn, GitHub; a visible identity line with the title and location on the first screen.
- **Share a link that previews properly.** A real 1200×630 OG image, titles and descriptions from the resume data.
- **Ask an assistant.** `/resume`, `/projects`, `/services`, `/profile`, `/now` as JSON on the API; the full content server-rendered on `/`.

Deliberately not added: analytics, a contact form, a blog, light mode, a 3D anything.

## 5. AI workflow, CI, repo organization

Replicated from `tallied` and `RigReady`:

- `CLAUDE.md` (read-first list, rules, quick start, layout), `docs/PRODUCT.md` (scope; source of truth), `docs/ARCHITECTURE.md`, `docs/CONTRIBUTING-FEATURES.md` (how to add a command, a content field, a page, an endpoint — and what evidence each needs), `docs/DEPLOYING.md`.
- `docs/requirements/ledger.yaml` + `scripts/ledger_check.py`: a requirement is done only with a test and, if visible, a screenshot from `make tour`.
- `Makefile` with `make pre-commit` = lint + typecheck + tests + build + content-check + ledger-check + catalog-check, the same list CI runs.
- `scripts/screenshot_tour.mjs` → `artifacts/screens/<name>/{mobile,desktop}.png`, failing on horizontal overflow; uploaded as a PR artifact.
- JSON Schemas for `content/` and `make content-check`, so an agent editing a fact gets told immediately when it breaks the shape.
- `make og-image` and `make resume-pdf` so generated assets are reproducible; CI fails when the PDF is older than the resume.
- Dependabot for npm (was missing), PR template, `concurrency` on the workflow, `.claude/worktrees/` ignored.

Why this matters for a repo "primarily worked on by AI": an agent opening this repo cold now gets the purpose, the rules, the commands to run and a machine-checked list of what is done and what isn't — instead of inferring the product from `useTerminal.ts`.
